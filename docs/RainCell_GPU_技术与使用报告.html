1. 交付结论

本轮已完成一个可直接在浏览器操作的 GPU 加速二维水流原型。系统能够：

  • 自动生成带多尺度山脊、主谷、支沟、南北总体落差和下游谷口的合成山区 DEM；
  • 在正方形计算域上设置位置、宽度、高度、强度和历时均可调的区域降雨；
  • 在 GPU 上连续推进降雨、入渗、水面坡度驱动、惯性、Manning 阻力、单元间守恒通量和开放谷口出流；
  • 实时显示 DEM、水深、流速和主导流向，并显示累计降雨、入渗、谷口出流、域内存储和质量闭合误差；
  • 在 CUDA 不可用或运行库不匹配时自动回退 NumPy CPU，以保证页面仍能运行。

该成果是教学、交互演示和算法筛查原型。合成 DEM 不是实际地区地形，模型尚未用标准水动力基准、实验室数据或真实山洪事件完成校准与独立验证，因此不能直接用于工程设计、人员安全判断或预警发布。

3. 模型结构

3.1 元胞状态

每个二维元胞保存：

  • 地面高程 z，单位 m；
  • 水深 h，单位 m；
  • 东西向和南北向单宽流量 qx、qy，单位 m²/s；
  • 由通量和水深派生的深度平均速度 u、v，单位 m/s。

其中水面高程为 H = z + h，湿单元的速度为 u = qx / h、v = qy / h。水深小于干湿阈值的单元速度和方向置为零，避免把干区数值噪声画成流向。

3.2 降雨与入渗

降雨强度从 mm/h 换算为 m/s，并只施加在可调的圆角矩形降雨掩膜内；到达设定历时后雨源自动停止。单步源汇更新为：

h* = h + r·Δt − min(h + r·Δt, f·Δt)

r 为降雨率，f 为常量入渗能力。当前版本没有表示入渗容量随土壤饱和度衰减；这是有意保留的简化。

3.3 局部惯性通量

相邻元胞面上的单宽流量使用局部惯性形式推进：

q(t+Δt) = [q(t) − g·h_f·Δt·(ΔH/Δx)]
          / [1 + g·Δt·n²·|q(t)| / (h_f^(7/3) + ε)]
  • h_f 是单元面上的有效过水深度；
  • ΔH/Δx 是相邻水面高程梯度；
  • n 是 Manning 糙率；
  • 分子保留上一时刻通量，表达局部惯性；
  • 分母表达床面摩阻。

该方法比只按邻格水位差“平均分水”的简单 CA 多保留了通量状态和惯性，但仍不是包含完整平流项的二维浅水方程有限体积求解器。在陡坡、激波、溃坝和复杂绕流中必须通过更严格基准后才能确定适用范围。

3.4 守恒更新与非负限制

每个单元按四个正交单元面共享同一份带符号通量，水量更新为：

h(t+Δt) = h* + (Δt/Δx)·(Σq_in − Σq_out) − outlet

更新前计算每个单元的总出流需求。如果预计出流超过单元可用水量，则按同一比例缩小该单元所有外流面通量。这样可以同时保证：

  • 单元水深非负；
  • 一条共享边上的流出与邻格流入完全相同；
  • 不依赖更新顺序；
  • 降雨、入渗、存储和谷口出流可统一记账。

3.5 时间步

程序采用 CFL 约束的自适应时间步：

Δt = min(Δt_max, CFL·Δx / max(|v| + sqrt(g·h)))

这使雨刚开始时可使用较大时间步，流速和水深增大后自动缩短时间步。默认 CFL = 0.35。

4. 合成山区 DEM

DEM 使用确定性随机种子生成，流程包括：

  1. 对四个空间尺度的随机场做高斯滤波并按权重叠加；
  2. 加入两条长山脊和非对称构造抬升；
  3. 叠加由北向南的总体落差；
  4. 刻蚀一条随下游逐渐展宽、轻微弯曲的主谷；
  5. 刻蚀两条汇入主谷的支沟；
  6. 在南侧边界形成可选开放谷口。
  7. 以谷口为唯一出口执行四邻域 priority-flood 水文整饰，抬高严格封闭的内部洼地并保留最小排水坡降，使每个单元至少存在一条通向南侧谷口的下降路径。

相同种子和参数会生成完全相同的 DEM。它比单一白噪声或简单斜平面更接近山区的多尺度形态，但没有模拟真实地质和河网演化；priority-flood 也只是用于保证演示域排水连通的数值整饰，不能代替真实 DEM 的专业水文修正。

5. GPU 实现

engine.py 使用统一数组运算接口：CUDA 可用时使用 CuPy，静态 DEM、雨区掩膜、水深和两个方向的面通量均常驻 GPU；只有浏览器需要显示一帧时才把量化后的水深、速度和方向传回 CPU。CUDA 初始化除检测显卡外还执行一个 NVRTC 内核探针，避免“能枚举显卡但不能编译内核”的假 GPU 状态。

浏览器收到的数据经过 16 位量化：

  • DEM：uint16；
  • 水深：uint16 + 当前帧比例尺；
  • 流速：uint16 + 当前帧比例尺；
  • 方向：两个 int8 单位向量分量。

量化只作用于显示帧，不改变 GPU 内部的 float32 计算状态。

6. 网页使用说明

6.1 启动

在终端运行：

cd /home/shyr/workspace/RainFall
./start.sh

看到启动提示后，在浏览器打开：

http://127.0.0.1:8000

如果 8000 端口已被占用：

RAINFALL_PORT=8010 ./start.sh

然后打开 http://127.0.0.1:8010。

6.2 基本操作

  1. 先查看右上角设备状态。显示 GPU · NVIDIA ... 表示 CUDA 已启用；显示 CPU 回退模式 表示仍可运行但会较慢。
  2. 调整“降雨强度、历时、中心 X/Y、区域宽度/高度”。橙色虚线框是降雨区域，参数会在运行中实时生效；到达设定历时后页面会显示“降雨已结束”，模型继续汇流和退水。
  3. 调整入渗能力和 Manning 糙率。较大入渗会减少地表产流，较大糙率通常会降低流速并延缓汇流。
  4. 选择是否打开下游谷口。打开后水可从南侧主谷出口离开计算域。
  5. 点击“开始”连续推进，点击“暂停”停止；“单帧推进”用于逐帧观察；“清零”保留当前参数并从无水状态重新开始。
  6. 使用“综合 / 水深 / 流速”切换图层。综合与流速视图会显示稀疏流向箭头；水深视图隐藏箭头以便观察淹没分布。
  7. 点击运行控制区的“↓”可将当前地图画面导出为带仿真秒数的 PNG 文件。
  8. 查看“WATER LEDGER”水量账本：降雨输入减去入渗损失和谷口出流，应与域内水量在浮点误差范围内闭合。
  9. 鼠标移动到地图上可查看单元坐标、水深和流速。
  10. 调整标有“重建”的 DEM 参数后，点击“生成新地形并清零”。

6.4 本地 API

服务启动后可打开 http://127.0.0.1:8000/docs 查看 FastAPI 自动生成的交互接口说明。主要接口为：

方法 路径 用途
GET /api/info 返回设备、后端、模型名称和当前配置
GET /api/frame 返回当前 DEM、量化水深/速度/方向和统计量
POST /api/reset 使用完整配置重建 DEM 并清零状态
PATCH /api/controls 运行中更新雨强、历时、雨区、入渗、糙率和出口
POST /api/step 推进 1–64 次 CA 迭代并返回新帧

服务默认只监听 127.0.0.1，不会自动暴露到局域网或互联网。若确需局域网访问，可设置 RAINFALL_HOST=0.0.0.0，但应先评估访问控制、防火墙和运行资源；本原型没有用户认证或多租户隔离。

当前服务进程只维护一个共享仿真状态。同一时刻打开多个页面会看到同一场景，而且多个页面同时点击“开始”会共同推进该场景；它适合单用户本地演示，不是多用户任务队列。

7. 已完成验证

7.1 自动化测试

本轮运行 10 项测试，全部通过：

  • DEM 同种子可复现、不同种子不同、具有足够高差且无严格封闭的内部洼地；
  • 直接降雨场景水深非负且质量闭合；
  • 降雨源在设定历时结束时精确停止，后续迭代不再增加累计降雨；
  • 平坦地形上的均匀静水不产生伪流；
  • 不规则地形上具有统一水面高程的静水不产生伪流，检查 well-balanced 性质；
  • 30° 斜平面上的二维通量方向与已知坡向误差小于 0.5°；
  • 直接放置在开放谷口的水量，其域内减少量与累计出流一致；
  • 初始水团在单向坡面上的质心向下游移动；
  • 首页、设备信息、重置、实时控制和推进接口正常；
  • 数据帧包含 DEM、水深、速度、方向和统计量。

7.2 CPU/GPU 一致性

在 96×96、60 步相同输入下，本次实测：

指标 结果
GPU NVIDIA GeForce RTX 5090
最大水深绝对差 3.4925×10⁻¹⁰ m
平均水深绝对差 7.5791×10⁻¹³ m
CPU 相对质量误差 1.6597×10⁻⁹
GPU 相对质量误差 5.1036×10⁻⁹

这证明当前 CPU/GPU 实现高度一致，不证明模型与现实一致。

7.3 本机 GPU 性能

RTX 5090、CUDA 13、每组预热后运行 5×32 步，本次实测如下：

网格 单元数 中位 step/s 最低 step/s 相对质量误差
96×96 9,216 550.2 389.9 8.34×10⁻⁸
192×192 36,864 463.3 402.7 3.80×10⁻⁷
256×256 65,536 500.0 409.8 3.96×10⁻⁷
384×384 147,456 518.5 407.3 2.92×10⁻⁷

小网格不能充分占满 RTX 5090，因此 step/s 没有随网格尺寸单调下降。这些数字只代表本机、当前场景和当前版本，不应外推到其他硬件或更复杂模型。

最大 384×384 网格还单独连续推进到 3,600 s（3,998 个自适应步）：状态保持有限、未出现负水深，末时相对质量误差为 4.995×10⁻⁸。这是一项长时数值稳定性检查，不是现实精度验证。

另以默认 192×192 网格、每帧 16 步重复执行两组各 20 次预热后的完整本地接口调用，覆盖 GPU 推进、速度统计、显示量化与 JSON/Base64 返回：中位响应均约 33 ms，观测 P95 为 36–43 ms，中位帧载荷约 289 KiB，对应不含浏览器最终绘制的理论上限约 30 frame/s。真实页面帧率还会受浏览器、显示分辨率和其他进程影响。

7.5 长时“降雨—汇流—退水”验证

为避免短时测试掩盖出口、累计误差或退水问题，本轮另外运行了一个 192×192 的 4 小时仿真：前 30 分钟在上部区域持续施加 200 mm/h 降雨，入渗设为 0，随后停止降雨并继续演算 3.5 小时。结果如下：

指标 结果
累计降雨入水 50,671.139 m³
4 小时末谷口累计出流 42,896.823 m³
4 小时末域内存储 7,774.310 m³
4 小时末最大水深 0.258 m
4 小时末最大流速 1.535 m/s
质量残差 −0.005 m³
相对质量误差 9.897×10⁻⁸

测试中水先在山坡与支沟汇集，约 1.5 小时后开始到达南侧谷口；停雨后域内存储持续下降。这验证了当前合成 DEM 水文整饰、共享通量、开放出口和长时间累计记账能够共同形成完整的“汇集—下泄—出域”过程。它仍属于合成场景代码验证，不是现实流域验证。
